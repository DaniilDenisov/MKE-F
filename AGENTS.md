# Работа с MKE-F

## Docker — основная среда выполнения

- Запуски приложения, расчёты, сборки, тесты и проверки инструментами (включая Gitleaks) по умолчанию выполняйте в Docker. Пользователь обычно не использует локальный Python/venv.
- Перед выполнением проверьте доступность Docker Engine и уже имеющиеся образы. Используйте подходящий существующий образ; при необходимости соберите образ из Dockerfile проекта или скачайте официальный образ инструмента.
- Если Docker Desktop выключен или Engine ещё не готов, явно попросите пользователя запустить Docker Desktop и дождаться готовности Engine. Объясните, какой запуск от этого зависит, и повторите проверку после ответа. Если Engine всё ещё недоступен, сообщите об этом и попросите проверить его запуск; не переходите молча к локальной среде.
- Ошибка доступа к Docker из песочницы не означает, что Docker выключен: сначала запросите необходимые разрешения для команды.
- Не создавайте локальный venv, не устанавливайте зависимости или отдельные исполняемые файлы на хост и не заменяйте Docker локальными Python/Node.js/Octave без явного указания пользователя. Пока Docker недоступен, продолжайте независимое чтение и редактирование файлов.
- Git, поиск и редактирование файлов можно выполнять на хосте. PowerShell-сценарии, которые управляют Docker-проверками, также запускайте на хосте.

## Команды и результаты

- Актуальные инструкции: `DEVGUIDE.md`, `scripts/README.md`, `tests/README.md`; состав релизных проверок: `scripts/testing/release-tests.json`.
- Полная приёмка: `pwsh -NoProfile -File ./scripts/testing/test_release.ps1`. Выполняйте подходящие задаче проверки; полная приёмка нужна не для каждой правки документации.
- Готовые тестовые образы: `mkef-solver-test:latest` и `mkef-browser-tests:latest`; Dockerfile находятся в `docker/`. Проверяйте актуальность образов относительно изменённых зависимостей.
- Исходники по возможности монтируйте только для чтения, результаты записывайте в отдельный каталог внутри `output/`. Не останавливайте чужие контейнеры и не выполняйте глобальную очистку Docker ради тестов.

## Проверка секретов через Gitleaks

- Плановые проверки выполняйте только перед созданием коммита — для подготовленных изменений (`gitleaks git --staged`) — и перед push — для отправляемых коммитов. Не запускайте Gitleaks после каждого редактирования, теста или ответа пользователю. Отдельный аудит выполняйте по явному запросу пользователя: проверяйте согласованный объём, при полном аудите — всю доступную историю (`gitleaks git --log-opts="--all --reflog --full-history"`) и текущие файлы (`gitleaks dir`), включая неотслеживаемые и игнорируемые. Указывайте фактический охват; неполный клон не позволяет проверить всю историю.
- Запускайте Gitleaks в Docker с `--network none`, исходниками только для чтения и отдельным каталогом отчётов. Используйте образ из официальной документации Gitleaks; фиксируйте проверенную версию или digest для воспроизводимости и указывайте версию в результате. Если Docker недоступен, следуйте правилам выше; самописный поиск не заменяет Gitleaks.
- Всегда используйте `--redact=100`. Не выводите значения секретов в чат, терминал, логи или коммиты. Для описания находки достаточно типа, пути, строки и идентификатора коммита. Отчёты храните в игнорируемом каталоге `output/`; не публикуйте их автоматически.
- Не отключайте стандартные правила и не скрывайте находки широкими исключениями каталогов. Для полного аудита учитывайте существующие исключения и используйте `--ignore-gitleaks-allow`, чтобы комментарии в коде не скрывали совпадения. Точечное исключение допустимо после проверки ложного срабатывания с описанием причины; имя файла вроде `test.key` само по себе этого не доказывает.
- При любой находке сообщите пользователю тип и расположение без значения секрета, предложите конкретный следующий шаг и спросите, как поступить. Дождитесь ответа: не удаляйте и не заменяйте секреты, не добавляйте исключения и не меняйте историю самостоятельно. Если находка относится к предстоящему коммиту/push, приостановите его до решения пользователя. Находки только в игнорируемых локальных файлах сообщайте отдельно от утечек в Git. Ошибка запуска сканера не означает успешную проверку.
- Если действующий секрет попал в общую историю, сначала сообщите о необходимости его отзыва или замены у провайдера. Удаление файла, ветки или добавление в `.gitignore` не обезвреживает опубликованный секрет. Переписывание истории и force push требуют отдельного согласования конкретного плана; не выполняйте их автоматически по результату сканирования.
- Успешная проверка означает «Gitleaks не обнаружил секретов в проверенном объёме», а не гарантию их отсутствия. Эти инструкции не устанавливают Git hooks или CI-проверки: автоматическое блокирование публикации требует отдельной настройки.

Источники: [Gitleaks](https://github.com/gitleaks/gitleaks), [действия при утечке секретов в GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).
