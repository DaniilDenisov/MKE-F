# Внутренний HTTP API сечений

Префикс `/api/v1/sections/`. Схемы запросов доступны по `openapi.json`, состояние сервера — по `health`.

| POST | Вход |
|---|---|
| `solve` | `section` (тип и размеры), `nu`, необязательные `J_model`, `options` |
| `point` | Те же данные, шесть `forces`, координаты `y`, `z`, необязательный номер стороны `element` |
| `maximum` | Данные сечения и шесть `forces` |
| `diagnostic` | Вход как у `maximum`. Метаданные `display` и сводка расчёта доступны в результате задания. |
| `member` | Данные сечения и шесть полиномов `coefficients` в осях профиля, при `include_mesh_peak=true` для сингулярной трубы возвращается `maximum.mesh_peak` последней завершённой сетки, либо `axial` и `area` для фермы |

Для проверки максимума можно отправить `{"section":{"type":"rectangle","dimensions":{"h":2,"b":1}},"nu":0.3,"forces":[0.1,1,-0.31,0.17,0.09,-0.06]}` в `maximum`. Ответ HTTP 202 содержит идентификатор. `GET jobs/{id}` возвращает `state` и по завершении `result` с численными статусами пакета. `DELETE jobs/{id}` отменяет задание. Состояние `completed` означает завершение операции. Для расчётного значения проверяются `result.status` и статусы соответствующих величин.

После `display.status="ok"` запросите `GET jobs/{id}/field` один раз. Двоичный формат v1 использует little-endian. Заголовок содержит четыре uint32 (версия, число узлов, число элементов, число делений ребра). Далее идут пары float64 (y,z), шесть uint32 на Tri6 (a,b,c,ab,bc,ca) и четыре float64 (σx,τxy,τxz,σVM) на каждую из 15 локальных точек. Порядок точек задают i=0…4, j=0…4−i с барицентрическими координатами ((4−i−j)/4,i/4,j/4). Лимиты составляют 24 MiB на поле и 48 MiB на сохранённые поля. При вытеснении поле получает статус `evicted`, сводка сохраняется. DELETE завершённого задания освобождает поле.

Один процесс Uvicorn управляет ограниченной очередью FIFO. Рабочий процесс повторно использует типоразмеры и поля между заданиями. При отмене активного задания или истечении времени сервер завершает процесс вместе с нативным вычислением. Очередь хранится в памяти. По умолчанию допускаются четыре активных и ожидающих задания суммарно, переполнение даёт HTTP 429. Доступны до 32 завершённых записей за последние 15 минут.

Проверка API из корня репозитория в PowerShell:

```powershell
docker build -f docker/section-solver.Dockerfile -t mkef-section-api:test .
docker run --rm --mount "type=bind,source=${PWD},target=/app" -w /app mkef-section-api:test python -m unittest discover -s tests/section_service -v
```

В сборке из исходников `docker compose up --build -d` запускает `section-solver` во внутренней сети. Nginx принимает запросы под тем же префиксом. Для контейнера по умолчанию выделены 2 CPU и 2 GiB. Настройки задают переменные `MKEF_SECTION_CPUS`, `MKEF_SECTION_MEMORY` и `MKEF_SECTION_QUEUE_CAPACITY`.

`./scripts/test_section_service_compose.ps1` проверяет расчёт через Nginx, доступность API стержневого решателя при остановленном сервисе сечений и восстановление маршрута. Проверка использует временный Compose-проект со свободным портом.

Общую панель σx/σVM проверяет `scripts/test_section_inspector_browser.cjs`: она обслуживает свежие файлы рабочего каталога и проксирует API к запущенному Compose. Сначала в Octave выполните `setup(); addpath('tests'); test_sections(); test_spatial_sections(); test_section_contract(); test_section_inspector();`. Затем запустите браузерный образ с `--network container:mkef-web-1`, рабочим каталогом `/app` и примонтированным репозиторием, командой `node scripts/test_section_inspector_browser.cjs`. Проверяются численные поля реального сервиса, 42 ориентации/профиля, чистое кручение, сжатие, отверстия, быстрые изменения координаты, кэш, запоздалые ответы, ошибки и экспорт. Скриншоты сохраняются в `output/section-inspector-*.png`.

`MKEF_SECTION_TEST_BACKEND` задаёт отдельный адрес сервиса сечений для изолированного прогона; остальные API идут через `MKEF_TEST_BACKEND` (по умолчанию `http://127.0.0.1:8080`). `MKEF_SECTION_REGRESSIONS=only` запускает проверки таблицы максимумов, диагностической страницы и каталога скруглений; им рекомендуется отдельный чистый экземпляр сервиса, поскольку длительная последовательность разных сеток может исчерпать его бюджет памяти.


Для квадратной и прямоугольной труб параметр `section.dimensions.inner_radius` задаёт внутренний радиус скругления. При положительном радиусе наружный радиус равен внутреннему плюс толщина стенки. По умолчанию углы острые. Радиус хранится в каталоге препроцессора и передаётся в результатах вместе с геометрией. Octave учитывает его в A, Iy, Iz и автоматическом приближённом J; Python использует ту же геометрию при восстановлении напряжений. После изменения радиуса необходим повторный расчёт модели. Ручное J остаётся явным переопределением жёсткости, а J_FE определяется геометрией.
