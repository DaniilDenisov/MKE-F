1. Docker Compose

Для основного сценария нужен Docker Desktop или Docker Engine с Compose. Установленный на компьютере GNU Octave не требуется: решатель GNU Octave 11.3.0 работает внутри контейнера.

Из корня репозитория выполните:

docker compose up --build

Эта команда собирает текущие исходники. compose.release.yaml использует готовые образы версии 0.8.4: возможности из раздела «Невыпущенные изменения» в CHANGELOG в них не входят.

Для старой отдельной команды Compose эквивалентный запуск выглядит так:

docker-compose up --build

После готовности контейнеров откройте http://127.0.0.1:8080. Создайте модель или загрузите TXT-файл, затем нажмите Run analysis. Интерфейс покажет состояние и журнал расчёта. После статуса Completed нажмите Open result: результат откроется в отдельной вкладке, а модель и история Undo/Redo останутся в редакторе.

Сохранение результата

Задания и результаты хранятся во временной файловой системе контейнера. Нужный JSON следует скачать до остановки стека.

Остановить приложение можно сочетанием Ctrl+C в его терминале. Удалить созданные контейнеры и сеть:

docker compose down

2. Настройка и ограничения

Снаружи публикуется только Nginx на loopback-интерфейсе. FastAPI и Octave доступны лишь во внутренней сети Compose. API принимает модель, но не произвольные скрипты, пути или выражения Octave. Один worker выполняет расчёты последовательно; остальные принятые задания ожидают в очереди.

Например, в PowerShell приложение на порту 8090 можно запустить так:

$env:MKEF_PORT = "8090"
docker compose up --build

3. Проверка проекта

Контейнерный smoke-тест

При работающем стеке запустите из корня репозитория:

./scripts/compose_smoke_test.ps1

Интеграционные тесты Python и Octave

docker build --target test -t mkef-solver-test -f docker/solver.Dockerfile .
docker run --rm mkef-solver-test

Браузерные проверки в Docker

Из корня репозитория соберите образ и запустите нужную проверку (команды подходят для PowerShell и Bash):

docker build -t mkef-browser-tests -f docker/browser-tests.Dockerfile .
docker run --rm -v "${PWD}:/app" -w /app --entrypoint node mkef-browser-tests scripts/test_reference_browser.cjs
docker run --rm -v "${PWD}:/app" -w /app --entrypoint node mkef-browser-tests scripts/test_unified_editor_browser.cjs
docker run --rm -v "${PWD}:/app" -w /app --entrypoint node mkef-browser-tests scripts/test_unified_post_browser.cjs

Для проверки Python-решателя сечений запустите ./scripts/section_solver_acceptance/run.ps1 в PowerShell. Отчёт охватывает пять профилей. Команда ./scripts/test_section_service_compose.ps1 проверяет диагностику через Nginx, остановку и восстановление сервиса.

4. Автономные веб-интерфейсы

preprocessor/index.html и postprocessor/index.html можно открыть прямо с диска. В таком режиме доступны создание и редактирование TXT-моделей, а также просмотр ранее сохранённых JSON-результатов. Запуск расчёта из препроцессора доступен только через контейнерный API.

Препроцессор

Редактор и постпроцессор используют общую WebGL-сцену. Для 2D камера фиксирована в XY; в 3D доступны вращение и рабочие плоскости XY/XZ/YZ. Создавайте узлы и элементы инструментами Add Node и Add Element; точные значения редактируйте в левой панели выбранного объекта. Таблицы объектов находятся справа. View управляет камерой, плоскостью, смещением и шагом сетки; Snap to grid и Snap to nodes — привязками. TXT открывается через Open TXT или перетаскиванием в окно.

Выбранный вид расчёта сохраняется в секции analysis. Её синтаксис и правила совместимости старых файлов приведены в описании формата.

Параметры анализа применяются при изменении полей; некорректные значения блокируют запуск. Результат относится к отправленному снимку модели. Сообщение Calculation completed. The solver produced no log messages. означает успешное завершение без сообщений в журнале. Без WebGL остаются доступны формы, таблицы, графики и SVG-разрез сечения; сцена и её PNG-экспорт недоступны.

Постпроцессор и единицы

Результаты сохраняются в JSON. Сцены 2D экспортируются в PNG/SVG, сцены 3D — в PNG. Также доступны SVG графиков и разрезов сечений, CSV численных данных. Формы, таблицы и графики доступны без WebGL, но экспорт сцены требует работающей WebGL-сцены.

Постпроцессор не преобразует численные значения. Обозначения берутся из metadata.units экспортированного JSON и должны соответствовать согласованной системе исходной модели. Амплитуда нормированной собственной формы произвольна и не является физическим перемещением.

5. Структура репозитория

КаталогНазначение
src/modelЧтение модели, элементы и сборка глобальных матриц.
src/analysisОбщие операции, статический, модальный и переходный решатели.
src/resultsВосстановление результатов, экспорт и графики.
preprocessorСоздание и редактирование входных TXT-файлов.
postprocessorПросмотр и экспорт результатов расчёта.
examples/casesПоставляемые входные модели.
examples/resultsГотовые JSON-примеры для постпроцессора.
referenceАвтономный учебный справочник и лабораторные.
scriptsТочки запуска тестов и служебных проверок.
tests/fixturesДанные для проверок ошибок и граничных случаев.
outputЛокальные результаты; содержимое не отслеживается Git.

6. Где искать остальные сведения

  • формат входного файла, единицы, элементы, опоры и нагрузки;
  • статический расчёт и статический вид постпроцессора;
  • модальный расчёт и анимация форм;
  • переходный расчёт, временные истории и спектр;
  • локальные усилия, деформации и напряжения элементов;
  • архитектура, разреженная сборка и карта проверок;
  • полный численный пример Mario Paz;
  • работа без Docker непосредственно в GNU Octave.

Проверки равномерных нагрузок

Полный набор run_octave_tests включает test_element_loads. Контейнерные тесты API проверяют CaseUniformFrame через настоящий GNU Octave. Браузерные наборы доступны по preprocessor/tests/, postprocessor/tests/ и shared/tests/.

Автоматические проверки общего редактора и постпроцессора запускаются в Docker командами выше. Скриншоты и отчёты сохраняются в output.
