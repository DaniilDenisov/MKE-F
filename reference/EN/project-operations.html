Appendix

Project operations

This appendix collects operational information moved from the root README. Theory, data formats and analysis examples remain in the topic chapters.

1. Docker Compose

The main workflow requires Docker Desktop or Docker Engine with Compose. No host GNU Octave installation is needed: GNU Octave 11.3.0 runs inside the container.

From the repository root, run:

docker compose up --build

The equivalent older standalone Compose command is:

docker-compose up --build

Once the containers are ready, open http://127.0.0.1:8080. Create a model or load a TXT file, then click Run analysis. The interface shows analysis status and logs, and the finished result opens automatically in the postprocessor.

Saving the result

Jobs and results are stored in the container’s temporary filesystem. Download any required JSON before stopping the stack.

Stop the application with Ctrl+C in its terminal. Remove the created containers and network with:

docker compose down

2. Settings and limits

Only Nginx is published on the loopback interface. FastAPI and Octave are accessible only within the Compose network. The API accepts models, not arbitrary scripts, paths or Octave expressions. One worker runs analyses sequentially; other accepted jobs wait in a queue.

docker compose up --build

3. Project verification

Container smoke test

With the stack running, execute from the repository root:

./scripts/compose_smoke_test.ps1

Python and Octave integration tests

docker build --target test -t mkef-solver-test -f docker/solver.Dockerfile .
docker run --rm mkef-solver-test

Browser application tests

Open these files from disk preprocessor/tests/index.html, postprocessor/tests/index.html and shared/tests/index.html. A successful result contains only PASS lines and a final passed-check count.

If your browser blocks local scripts, run from the repository root:

python -m http.server 8000

Then open preprocessor tests, postprocessor tests and shared tests. Stop the server with Ctrl+C.

Local numerical-core tests and GNU Octave requirements are described in chapter 12.

4. Offline web interfaces

preprocessor/index.html and postprocessor/index.html can be opened directly from disk. This mode supports creating and editing TXT models and viewing saved JSON results. Running an analysis from the preprocessor requires the container API.

Preprocessor

Create nodes and elements on the SVG canvas; edit exact coordinates, properties, supports and loads in tables. Open a TXT file with Open TXT or drag it into the window. Configure the coordinate grid, its size and snapping step in the Canvas settings panel; selected-node coordinates are also available in the Selection.

The chosen analysis type is saved in section analysis. Its syntax and old-file compatibility rules are in the format description.

Postprocessor and units

The postprocessor does not convert numbers. Labels come from metadata.units in the exported JSON and must match the input model’s consistent unit system. A normalized eigenvector has arbitrary amplitude and is not a physical displacement.

Uniform-load checks

The complete suite run_octave_tests includes test_element_loads. Container API tests run CaseUniformFrame through actual GNU Octave. Browser suites are available at preprocessor/tests/, postprocessor/tests/ and shared/tests/.

For automated interface checks, install Playwright in the development environment, export CaseUniformFrame to output/uniform-result.json and run node scripts/test_browser.cjs. If needed, the variable MKEF_PLAYWRIGHT_MODULE specifies the installed Playwright module path. The script checks cascading deletion, Undo/Redo and JSON v2 reading, and saves screenshots in output.
