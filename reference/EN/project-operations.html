Appendix

Project operations

This appendix collects operational information moved from the root README. Theory, data formats and analysis examples remain in the topic chapters.

1. Docker Compose

The main workflow requires Docker Desktop or Docker Engine with Compose. No host GNU Octave installation is needed: GNU Octave 11.3.0 runs inside the container.

From the repository root, run:

docker compose up --build

This command builds the current source. For the prebuilt release, use docker compose -f compose.release.yaml up -d. compose.release.yaml pins version 0.8.6 for three services: the Octave solver, Python section service and web interface. See CHANGELOG (Russian) for release history.

The equivalent older standalone Compose command is:

docker-compose up --build

Once the containers are ready, open http://127.0.0.1:8080. Create a model or load a TXT file, then click Run analysis. The interface shows analysis status and logs. After Completed, click Open result to open a separate postprocessor tab while preserving the editor and its Undo/Redo history.

Saving the result

Jobs and results are stored in the container’s temporary filesystem. Download any required JSON before stopping the stack.

Stop the application with Ctrl+C in its terminal. Remove the created containers and network with:

docker compose down

2. Settings and limits

Only Nginx is published on the loopback interface. FastAPI and Octave are accessible only within the Compose network. The API accepts models, not arbitrary scripts, paths or Octave expressions. One worker runs analyses sequentially; other accepted jobs wait in a queue.

$env:MKEF_PORT = "8090"
docker compose up --build

3. Project verification

Full release acceptance

Requires PowerShell 7+ and a running Docker engine with Compose. From the repository root:

pwsh -NoProfile -File ./scripts/testing/test_release.ps1

The runner builds images and executes Octave, NAFEMS quick/full, all registered JavaScript and browser tests, backend, the Python section solver and API, numerical acceptance and application checks in a separate Compose project. Fixtures are generated afresh; the working stack is not stopped. Temporary containers and image tags are removed after verification.

The report.md and report.json reports, plan, logs and artifacts are saved under output/release-runs/<run-id>/. Exit code 0 and a final PASS require every stage to succeed. Independent checks continue after failures; dependent stages become BLOCKED, which prevents acceptance. Do not edit sources during a run.

-PlanOnly validates the test inventory and displays the plan without Docker; -StageTimeoutSeconds changes the external command timeout (3600 seconds by default). Register new tests in scripts/testing/release-tests.json and the execution plan; an unregistered file fails verification. The commands below remain available for targeted checks.

Container smoke test

With the stack running, execute from the repository root:

./scripts/testing/compose_smoke_test.ps1

Python and Octave integration tests

docker build --target test -t mkef-solver-test -f docker/solver.Dockerfile .
docker run --rm mkef-solver-test

Browser checks in Docker

First generate fresh Octave results for the handbook and postprocessor checks. This uses the solver test image built above and saves data under output/:

docker run --rm -v "${PWD}:/app" -w /app --entrypoint octave-cli mkef-solver-test --no-gui --quiet --eval "setup(); run_octave_tests(); prepare_release_fixtures();"

Build the image and run the required check from the repository root (PowerShell or Bash):

docker build -t mkef-browser-tests -f docker/browser-tests.Dockerfile .
docker run --rm -v "${PWD}:/app" -w /app --entrypoint node mkef-browser-tests tests/browser/test_reference_browser.cjs
docker run --rm -v "${PWD}:/app" -w /app --entrypoint node mkef-browser-tests tests/browser/test_unified_editor_browser.cjs
docker run --rm -v "${PWD}:/app" -w /app --entrypoint node mkef-browser-tests tests/browser/test_unified_post_browser.cjs

For the Python section solver, run ./scripts/testing/run_section_solver_acceptance.ps1 in PowerShell. The report covers five profiles. Run ./scripts/testing/test_section_service_compose.ps1 to check the diagnostic page through Nginx, including service outages and recovery.

4. Offline web interfaces

preprocessor/index.html and postprocessor/index.html can be opened directly from disk. This mode supports creating and editing TXT models and viewing saved JSON results. Running an analysis from the preprocessor requires the container API.

Preprocessor

The editor and postprocessor share a WebGL scene. The 2D camera stays in XY; 3D supports orbiting and XY/XZ/YZ work planes. Create geometry with Add Node and Add Element; edit exact values in the selected object’s left panel. Object tables are on the right. View controls the camera, plane, offset and grid step; Snap to grid and Snap to nodes control snapping. Open TXT files with Open TXT or by dropping them into the window.

The chosen analysis type is saved in section analysis. Its required syntax are in the format description.

Analysis parameters apply when fields change; invalid values block a run. The result belongs to the submitted model snapshot. Calculation completed. The solver produced no log messages. means success with an empty log. Without WebGL, forms, tables, charts and the SVG section view remain available; the scene and its PNG export are unavailable.

Postprocessor and units

Save results as JSON. Export 2D scenes as PNG/SVG and 3D scenes as PNG. SVG charts and section cuts, and CSV numerical data are also available. Forms, tables and charts remain available without WebGL, but scene export requires a working WebGL scene.

The postprocessor does not convert numbers. Labels come from metadata.units in the exported JSON and must match the input model’s consistent unit system. A normalized eigenvector has arbitrary amplitude and is not a physical displacement.
