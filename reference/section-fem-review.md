# Ревизия реализации template-tri6-v2

> Historical record of the implementation available at `f355300`. For the current Python calculation and Docker verification, see [section field diagnostics](EN/08-result-recovery.html#section-fem-title).

Дата: 2026-11-02. Проверена реализация `PLAN-section-fem-template-meshes.md`
после `354b13c`, ветка `codex/spatial-solvers`. Исходный план не изменён.
Исправления относятся к изолированному FEM-модулю, его проверкам и документации.
Рабочий постпроцессор, каталог, форматы и глобальные решатели не изменены.

## Найденные ошибки и исправления

| Ошибка | Исправление и воспроизводимая проверка |
| --- | --- |
| При заданных `layers`/`segments` адаптивный расчёт повторял одну сетку и мог выдавать `ok` | Количества задают начальную сетку и удваиваются. Для кольца d=2, t=0.9, segments=512, layers=1 прежняя история была `[3072,3072,3072]` DOF; при Vy=1 значение tauXY(0.11,0) было 0.449733 вместо аналитического 0.075574. Теперь этот случай не получает `ok`. `test_section_fem_refinement.cjs`. |
| Сравнение полей пропускало элементы из-за фиксированного шага выборки | Семиточечная квадратура на каждом элементе, контроль покрытия. Тест вносит ошибку в ранее пропускаемый элемент и обнаруживает её. |
| Критерии зависели от размерного масштаба; квадрат нормы мог обнулиться/переполниться | Сравниваются безразмерные поля; удалены абсолютные добавки в критериях поиска/изменения пика. Размерный J вычисляется без промежуточного `scale**4`. `test_section_fem_scale_accuracy.cjs`: масштабы 1e-60 и 1e60, нагрузка 1e-80, большое конечное J. |
| Для максимума проверялось одно изменение сетки вместо двух последовательных сгущений | Сравниваются три пика, оба изменения должны быть ≤0.5%. Старая сетка восстанавливается лениво в общем бюджете; параметры её исходного решения сохраняются. `test_section_fem_recovery.cjs` и искусственный нестабильный старый пик в `test_section_fem_refinement.cjs`. |
| При поиске по длине интервалы с низкими концами исключались без оценки внутреннего пика | Для каждого интервала вычисляется верхняя оценка по вторым производным усилий и единичным полям. 80 смешанных кубических историй проверяются по независимым корням производной полинома квадрата нормы степени 6. `test_section_fem_length_bounds.cjs`. |
| Кэш обходил часть проверок параметров; оценка памяти выполнялась после выделения массивов | Общая предварительная проверка сетки до кэша/сборки, безопасные целые количества, учёт удерживаемых сеток и памяти поиска. Тест доказывает, что запрещённая вторая сборка не запускается. Остановка сохраняет последний kernel, J и историю. |
| Некоторые ветви возвращали `ok` с Infinity или игнорировали отмену | Проверка конечности нормальных/ферменных напряжений и нормы RHS, полных массивов усилий/полиномов, параметров поиска и отмены перед быстрыми и кэшированными ветвями. Строгая итоговая невязка без множителя 1.01; исключено повторное изменение среднего уже проверенного решения. |
| Ответ о сингулярном пике мог заменить переданный `J_model` каталожным и потерять причину остановки ядра | Worker сохраняет исходный `J_model`, согласованные различия во всех диагностических полях и отдельный `kernelStatus`; неизвестные операции и недопустимые адаптеры отвергаются. `test_section_fem_contracts.cjs`, offline/hosted браузерные проверки. |
| Worker заново отсчитывал `maxMs` после решения сечения при переходе к поиску пика/по длине | Все фазы запроса получают один дедлайн. Контрактный тест проверяет его конечность и равенство в решении и поиске; браузерный Worker проверен повторно. |
| Проверка потока только в середине граничного ребра скрывала антисимметричную ошибку | Три точки Гаусса на ребро, отдельная проверка убывания остатка на внешнем/внутреннем контурах, слабого равновесия с кубическими пробами и упругой совместности. `test_section_fem_equilibrium.cjs`. |

Обновлена версия метода и ключей кэша: `template-tri6-v2`. Вывод оценки по длине
и контракты приведены в [описании метода](section-fem-methods.md).

## Воспроизведение и ограничения

Все численные, браузерные и сборочные проверки выполняются в Docker:

```powershell
docker run --rm --mount type=bind,source=C:\Users\user\Desktop\MKE-F,target=/app --workdir /app --entrypoint node mkef-browser-tests:latest scripts/test_section_fem_regression.cjs --full
docker run --rm --mount type=bind,source=C:\Users\user\Desktop\MKE-F,target=/app --workdir /app --entrypoint octave-cli mkef-solver-test:latest --no-gui --quiet --eval "setup(); run_octave_tests();"
docker run --rm --mount type=bind,source=C:\Users\user\Desktop\MKE-F,target=/app --workdir /app --entrypoint python3 mkef-solver-test:latest -m pytest -q -p no:cacheprovider backend/tests/test_spatial_runner.py
```

Образы: browser `sha256:599c195ffec80828e7132f791c12e3532861058583fcfa88508eb9a9c4040df8`
(Node v24.21.0); solver
`sha256:56f9e54cf218289db9051d5604bbd58c404367b51196ebe5e712c92e45448f9c`
(GNU Octave 11.3.0, Python 3.14).
Результаты JS-прогонов и индивидуальные логи:
`output/section-fem/regression.json` (интеграция), `regression-full.json`,
`regression-quick.json`, `regression-selected.json`, `test_*.log`.
Новый runner записывает состояние `running` перед запуском и результат после
каждого теста; stdout/stderr сразу попадают в файл. Прерывание больше не оставляет
отчёт предыдущего прогона единственным свидетельством состояния текущего.
Численные отчёты: `recovery.json`, `shear.json`, `equilibrium.json`,
`tubes.json`, `tube-peaks.json` в том же каталоге. Они игнорируются Git.

В первом прогоне самая густая прямоугольная труба остановилась по времени.
Отдельный диагностический расчёт завершился за 57.4 с, 6779 итераций,
относительная невязка 1.04e-11. Для численного эталонного теста труб задан
отдельный предел 180 с, чтобы загрузка машины не определяла его исход.
Рабочий предел 60 с и все допуски точности сохранены. Увеличение времени
не гарантирует сходимость произвольной угловой сетки.

После полного сравнения полей прямоугольнику 1:10 потребовался уровень 4
(165249 DOF): на уровне 2 изменение Vz равно 0.658%, на уровнях 3 и 4 —
0.183% и 0.0498%. Поэтому прежний ранний выход больше не допускается.
Рабочий бюджет 60 с дал `resource_limit`; отдельный расчёт с исходным
автовыбором предобусловливателя подтвердил сходимость за 135.1 с при лимите 180 с.
Benchmark точности теперь явно использует лимит 180 с и существующую опцию
`preconditioner:'ic0'` для прямоугольников 1:10/10:1; параметры каждого случая
сохраняются в `benchmarks.json`. Это не изменение рабочего предобусловливателя,
лимитов или критериев приёмки. На других машинах время может отличаться.

Граничный поток на конечной сетке не тождественно нулевой: естественное условие
выполняется слабо, а круг аппроксимируется многоугольником. Новые проверки
контролируют уменьшение этого остатка, а не объявляют точность по значению
в единственной точке ребра. Верхние оценки поиска относятся к решённому
FEM-полю; они не являются строгой оценкой полной физической ошибки.

Для труб с острыми внутренними углами глобальный пик при Vy/Vz/T остаётся
`unavailable`, `singularPeak:true`; J и проверенные точки вдали от углов имеют
отдельные статусы. Радиусы и исключаемые зоны не добавлялись. Память ограничивается
оценкой хранения данных и отдельным лимитом LRU, а не жёстким пределом RSS процесса.
Новый расчёт по-прежнему запускается только явно через диагностический API/страницу.

## Скорость проверок

Длительная численная матрица — повторяющаяся стоимость полной приёмки,
а не разовый прогрев Docker. В измеренном прогоне тест полей сдвига занял
162 с; 122 с из них приходятся на прямоугольники 1:10 и 10:1 при пяти ν.
Тест комбинированных пиков занимает около 45 с; проверка J/топологии труб —
160 с. Трубы дополнительно требуют
независимого FVM-эталона и решения на сильно сгущённых угловых сетках.
Такие проверки нужны после изменения численного метода и перед приёмкой;
повторять их после каждого изменения документации или интерфейса не требуется.

Устранена лишняя 30-секундная работа в тесте сгущения: дефект повторяющейся
сетки проверяется на трёх небольших реальных сетках за 0.73 с. Исторический
пример с 512 сегментами выше сохранён как описание найденной ошибки.
Вся короткая проверка (8 тестов и 2 проверки сборок) прошла за 8.98 с.
Допуски, набор полной численной матрицы и рабочие бюджеты не ослаблялись.

```powershell
# Обычная работа над FEM: около 9 секунд на проверенной машине.
docker run --rm --mount type=bind,source=C:\Users\user\Desktop\MKE-F,target=/app --workdir /app --entrypoint node mkef-browser-tests:latest scripts/test_section_fem_regression.cjs --quick
# Повторить только необходимые тесты, не пересчитывая всю матрицу.
docker run --rm --mount type=bind,source=C:\Users\user\Desktop\MKE-F,target=/app --workdir /app --entrypoint node mkef-browser-tests:latest scripts/test_section_fem_regression.cjs --only=test_section_fem_tubes,test_section_fem_tube_peaks,benchmark_section_fem
```

`--quick` не заменяет независимую полную приёмку и браузерные проверки.
Без флагов запускается интеграционный набор; `--full` добавляет полную
численную матрицу. `benchmark_section_fem` отдельно обновляет десять приёмочных
случаев, JSON, рисунки и HTML; оценка памяти теперь включает все удерживаемые сетки.
